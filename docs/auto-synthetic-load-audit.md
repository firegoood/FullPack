## Scope and method

- Source engine: the v1.9.3 implementation at repository base
  `1b5f0737291ab238d48c27e4efd23e60215d541a` (documentation after release
  source `057f69d2a9d418f95196c1a9d54759e348e945d4`). Only the diagnostic
  tool, evidence and preservation guards are added in this task.
- `tools/auto-load-audit` generates 500 and 800 distinct, fresh Shadowsocks
  AES-256-GCM accounts in an isolated copy of the installed Xray version.
  Its [AEAD client follows the Shadowsocks specification](https://shadowsocks.org/doc/aead.html).
  Test secrets stay in memory/stdin, never in argv, reports or production config.
- The initial smoke check exposed Xray's default private-address outbound block,
  not an AEAD/FullPack failure. The isolated fixture explicitly permits only its
  generated `127.0.0.1` echo port using an outbound
  [`finalRules` allow entry](https://xtls.github.io/en/config/outbounds/freedom.html).
  The installed Xray policy stays unchanged. Failed smoke output is retained
  separately and is not included in load results.
- Compare plain TCP echo, authenticated Xray directly, and Xray through one
  enrolled encrypted Auto TCP carrier at its actual 64 and 192 connection limits.
  Burst workloads retain accepted connections until all attempts have returned,
  then verify those connections still exchange a unique 1024-byte challenge.
- For each account, test one and two simultaneous connections. A paced case
  limits outstanding attempts to 32 while using the same complete user set.
  Report fully connected, partly connected and failed synthetic users separately.
- A separate UDP case fills 64 authenticated associations, checks new TCP,
  closes the UDP clients and measures when Auto releases that shared capacity.
- Record application latency, EOF/reset/timeout/integrity errors, peak RSS,
  descriptors, goroutines, process CPU ticks, Auto admission, post-close release,
  the reported health state and active generation.
  Per-process peaks are sampled at 100 ms and are lower bounds on instantaneous
  RSS/descriptor peaks; the systemd memory high-water mark is recorded separately.

## Isolation

The diagnostic runs as `nobody` in a private network namespace. Every generated
listener and destination is IPv4 loopback. No WAN traffic is generated by the
load audit. A transient systemd unit bounds CPU, memory, descriptors, tasks and
runtime, denies access to production FullPack/FireNode configuration directories
and allows writes only in its private temporary fixture directory.

The installed Xray binary is copied for explicit test use only; it is not adopted
as a managed Auto helper. Production Xray/FullPack processes and fencing state
are retained. The binary hash/version and cgroup conditions accompany results.
No source, helper download, signature policy or production admission ceiling is
changed to make this workload pass.

Actual lab limits: one CPU core (`CPUQuota=100%`, `GOMAXPROCS=1`) on a two-core
host, 512 MiB cgroup memory, no swap, 128 kernel tasks, 16,384 descriptors and a
900-second watchdog. All synthetic clients, both Auto managers and the echo
backend share the harness process; Xray is a separate child in the same cgroup.
These CPU/RSS numbers are not per-host production capacity estimates.

## Reproduction

Build on patched Go 1.27.2:

```sh
go build -trimpath -o auto-load-audit ./tools/auto-load-audit
sudo bash tools/auto-load-audit/run-isolated.sh \
  ./auto-load-audit /explicit/path/to/installed/xray ./new-measurements.json
```

Without `--run` and an explicit fixture binary the program refuses execution.
It accepts no remote target option. The approximately one-minute UDP retention
case can be omitted for a small fixture smoke check with `--skip-udp-hold`.
The wrapper copies the explicitly supplied executables, runs as `nobody` with
the recorded isolation, retains a report/log and removes only its own fixture.
It refuses to overwrite an existing result. It does not install helpers.

## Results

Completed 2026-10-15 11:27:51–11:29:53 UTC (14:57:51–14:59:53 Tehran).
The earlier eight-account smoke check passed before this run. The main run
completed all sixteen phases plus the UDP retention test with no invariant
errors. [Machine-readable measurements](verification/auto-load-20261015.json)
include every case, error category, percentile, resources and user accounting.

The table counts **connections verified**, not users served. Burst results hold
each accepted connection open until all attempts complete. Every accepted
connection then passes a second independent echo on the same stream.

| Scenario | 500 identities × 1 connection | 500 × 2 | 800 × 1 | 800 × 2 |
| --- | ---: | ---: | ---: | ---: |
| Plain TCP, direct echo | 500/500 | — | 800/800 | — |
| Xray AES-256-GCM directly | 500/500 | 1000/1000 | 800/800 | 1600/1600 |
| Auto, enrolled limit 64, burst | 64/500 | 64/1000 | 64/800 | 64/1600 |
| Auto, enrolled limit 192, burst | 192/500 | 192/1000 | 192/800 | 192/1600 |
| Auto limit 64, external client pacing at 32 attempts | — | 1000/1000 | — | 1600/1600 |

- All overflow errors were EOF or reset, with no timeout/integrity errors.
  Examples: 800 one-connection identities at limit 64 produced 676 EOFs and
  60 resets; 800 two-connection identities at limit 192 produced 381 EOFs and
  1027 resets. Successful streams remained valid during overload.
- Auto continued reporting `HEALTHY` in every saturated burst. Both peers kept
  their agreed active generation. Every TCP test released admission back to zero
  after its clients closed; no persistent TCP capacity leak was observed.
- Direct Xray's success latency P95 rose from 615 ms (500 one-connection
  identities) to 3305 ms (800 two-connection identities). This is measurable
  processing/scheduling cost in the bounded one-core lab, but it did not cause
  the sharp 64/192 cutoff: the same 1600 requests all passed directly.
- Sampled maximum RSS: harness 104,868 KiB, Xray 290,736 KiB. Maximum sampled
  harness descriptors: 6595, below its 16,384 limit. The whole cgroup peaked at
  400,674,816 bytes (382.1 MiB), below 512 MiB, used 19.292 CPU seconds and ran
  for 121.422 seconds. There was no fixture OOM or production process restart.
- The Xray fixture was version `26.5.9`, SHA-256
  `b2c525e082cf2fef460499c88838d355f0b9bfb5a00bdb3eaa99b6af63825006`.
  The harness was built with Go 1.27.2; its ELF SHA-256 was
  `a64c2dbfd787e1bee41970b26ad4c5c674ac95f47c81f9fe0212c1c753325925`.

### Shared UDP/TCP capacity

Sixty-four distinct authenticated Shadowsocks UDP associations filled a fresh
limit-64 pair. A new valid TCP request was reset. Closing all 64 UDP clients
did not free the server associations: two seconds later all slots remained held
and another valid TCP request was reset. Capacity released after 60.077 seconds;
the next valid TCP request passed, with generation still 2.

This reproduces a second availability bottleneck: the same admission channel
serves TCP and UDP, and UDP association inactivity can deny all new TCP until
expiry. It is distinct from the bounded per-source UDP packet queue. It is a
demonstrated failure mechanism, not proof that all original TR/NL errors in the
13:10–13:25 incident were caused by this exact traffic mix; historical admission
categories were not recorded by the installed build.

### Implications and follow-up scope

The first hard cutoff in these workloads is Auto's enrolled connection limit.
Moving to 192 alone still rejects most simultaneous 500/800-user requests, and
is a paired-policy change requiring coordinated enrollment and retained fencing.
The paced case is load-generator pacing, **not a newly implemented production
queue**. It proves that the configured identity count itself is not a 64-user
restriction.

Production work should separately address bounded admission/queuing and required
connection capacity, TCP/UDP fairness and UDP association lifetimes, and truthful
capacity/backend/data-path health with typed rejection counters. It must retain
resource bounds, crypto/enrollment and recovery ownership. This diagnostic task
does not implement or deploy those changes, and does not raise the existing
192-connection hard ceiling.

The test units and child Xray processes exited; production service PIDs and
restart counters were unchanged. Only the scoped test artifacts are removed
after retaining reports. No operator accounts, listener ports, firewall rules,
tunnel manifests, keys or generation files were changed.

## Limits

WAN 500/800-user acceptance, sustained bandwidth, real application session mixes,
24-hour soak and capacity beyond the enrolled 192-connection ceiling are
**NOT VERIFIED**. Accounts configured in Xray are not a count of concurrent
independent users. Deliberately rejected overflow is an observed policy outcome,
not successful service to the rejected users.
